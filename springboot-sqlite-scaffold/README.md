# Spring Boot + Maven + SQLite scaffold

API scaffold with:

- Java 10 source/target
- Spring Boot 2.1.18.RELEASE
- Maven-compatible project
- SQLite by default
- PostgreSQL example profile for switching to a conventional SQL server
- JPA/Hibernate code-first schema (`ddl-auto=update`)
- Generic `IRepository<T, ID>` abstraction
- Example entity: `Example`
- Bearer token generated by `/auth/token`
- Token lifetime tied to the servlet `HttpSession`

## Important Java version note

There is no standard OpenJDK release named `10.0.12`. The project is configured for Java language level 10. If your runtime is actually a vendor build whose version string contains `10.0.12`, verify it reports Java major version 10 with `java -version`.

Spring Boot 3.x is intentionally not used because it requires Java 17 or newer.

## Requirements

- JDK 10
- Maven 3.9.x

This project ships with project-local Maven settings in `.mvn/` so it does **not** inherit the corporate/global machine settings. It is configured to use:

- local repository: `~/.m2/repository`
- Maven Central

Check:

```bash
java -version

```

## Run with SQLite

SQLite is the default profile:

```bash
mvn spring-boot:run
```

Profile selection is controlled by Spring profiles:

- `application.properties` -> `spring.profiles.active=local` (default)
- `application-local.properties` -> SQLite datasource (local only)
- `application-dev.properties` -> SQL datasource (intended for Railway/PostgreSQL)
- `application-prod.properties` -> SQL datasource (production)

To run explicitly with `dev` SQL profile:

```bash
mvn spring-boot:run -Dspring-boot.run.profiles=dev
```

By default, the SQLite database file is created at:

```text
${user.home}/springboot-sqlite-scaffold-local.db
```

You can override the location for local tests with:

```bash
SQLITE_DB_PATH=/absolute/path/to/app.db
```

When running with the `local` profile, the app seeds a local admin user if it does not exist:

- email: `admin@local`
- password: `admin123`
- role: `ADMIN`

Hibernate creates/updates the `examples` table from the `Example` entity.

## Run with PostgreSQL instead

```bash
DB_URL=jdbc:postgresql://localhost:5432/app \
DB_USERNAME=app \
DB_PASSWORD=app \
mvn spring-boot:run -Dspring-boot.run.profiles=sql
```

No application/repository code changes are required.

## Authentication flow

### 1. Generate a session token

```bash
curl -i -X POST http://localhost:8080/auth/token
```

Response example:

```json
{
  "token": "...",
  "type": "Bearer"
}
```

The token is stored in memory and associated with the servlet session that created it.
It remains valid until the session expires, is invalidated through logout, or the application restarts.

### 2. Call a protected endpoint

```bash
curl -H "Authorization: Bearer YOUR_TOKEN" \
  http://localhost:8080/api/examples
```

### 3. Create an example

```bash
curl -X POST \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name":"demo"}' \
  http://localhost:8080/api/examples
```

### 4. Logout / invalidate the session

To explicitly destroy the same HTTP session via `/auth/logout`, retain and send the `JSESSIONID` cookie returned by `/auth/token`:

```bash
curl -c cookies.txt -X POST http://localhost:8080/auth/token
curl -b cookies.txt -X POST http://localhost:8080/auth/logout
```

Once the session is destroyed, its token is removed.

## Repository pattern

Application code depends on:

```java
public interface IRepository<T, ID> {
    T save(T entity);
    Optional<T> findById(ID id);
    List<T> findAll();
    void deleteById(ID id);
}
```

`ExampleRepository` specializes this contract and `ExampleJpaRepository` implements it with JPA's `EntityManager`.

SQLite and PostgreSQL therefore share the exact same repository implementation; switching the database is configuration-only.

## Security note

This token mechanism is intentionally minimal and matches the requested session-lived behavior. It is not OAuth2/JWT and is not suitable as-is for an internet-facing production system. For production, use Spring Security with a proper authentication provider, HTTPS, CSRF/session strategy as appropriate, and persistent/distributed session/token storage if the application runs on multiple instances.
